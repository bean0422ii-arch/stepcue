## 1. 사용한 도구
| 도구 | 용도 |
|---|---|
| Claude Code (VS Code 확장, 모델: Claude Opus) | 주제 구상, 일정 계획, 문서 초안(Problem card, 설계, 이메일), 데이터 탐색 코드, 다이어그램 코드, Git 설정 |

**규칙**
- 공개 데이터셋(Daphnet)만 사용한다. 실제 개인 정보나 건강 데이터는 AI에 넣지 않는다.
- 이름과 학번 같은 개인 정보는 AI가 만든 파일에 넣지 않고, 메일 작성 창에서 직접 넣었다.
- AI가 만든 코드는 실행해서 결과를 확인하고, 설명할 수 있는지 스스로 점검한다.

## 3. 중요한 프롬프트 후보 (15주차에 5개 고르기)
1. **"공개데이터로 에이전트를 어떻게 학습하고 어떻게 테스트한다는거야"**
   → 계획의 약점(템포 밴딧은 검증 불가)을 드러낸 질문. 설계를 바꾸는 계기가 됨.
2. **"너가 쓴 이메일에 내가 보낸 이미지에서 요구하는 내용을 다 포함하고 있는지 확인해줘"**
   → AI 결과물을 원본 요구사항과 대조하게 해서 누락과 마감일 오류를 잡음.
3. **"큐 템포를 어떻게 조정할 수 있는지 다시 한번 더 설명해줘"**
   → 어떤 부분이 실제 데이터로 검증 가능한지 구분하게 됨.
4. (11/11) 슬라이드 예시와 겹치지 않는 주제를 요구한 프롬프트
   → 그대로 따라 하지 않고 나만의 주제를 정하게 됨.

## 4. AI가 틀린 것 후보 (15주차에 1개 고르기)
| # | AI가 틀린 것 | 어떻게 발견했나 | 결과 |
|---|---|---|---|
| **A** | 계획 단계에서 **"템포별 회복 시간을 학습해 다음 템포를 고른다(밴딧)"**를 핵심 기능으로 제안했다. 하지만 녹화된 데이터 속 환자는 우리 큐를 듣지 못하므로, 템포에 따라 회복 시간이 달라지는 걸 **검증할 방법이 없었다.** | "공개 데이터로 에이전트를 어떻게 테스트하냐"고 직접 물어봤을 때 드러남 | 밴딧을 빼고, 실제 데이터로 계산할 수 있는 "개인 걸음 속도 기반 템포"로 교체 |
| B | 이메일 마감을 **"월요일(11/16) 수업 전"**으로 적었다. 실제 공지는 **11/15(일) 23:59**였고, 필수 항목인 **Team Name**도 빠져 있었다. | 교수님 공지 원문을 AI에게 주고 하나씩 대조시킴 | 마감일과 항목을 고쳐서 기한 안에 발송 |
| C | README 조건 "under 5 commands"를 "5개 이하"로 적었다(정확히는 5개 미만 = 4개 이하). | 원문 문장 뜻을 물어봤을 때 AI가 스스로 정정 | 목표를 4개 이하로 변경 |

> 추천: **A**. 설계 자체를 바꾼 사례이고, "AI가 그럴듯하게 제안해도 데이터로 검증할 수 있는지 따져봐야 한다"는 교훈이 분명하다.
