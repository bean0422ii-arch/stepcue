# Problem Card: StepCue

> 11주차 제출. **무엇을, 왜** 푸는지 정리한 문서. **어떻게** 만드는지는 [design.md](design.md) 참고.

## 1. 프로젝트
**StepCue**: 파킨슨 보행동결(FoG)을 엣지에서 감지하고, 그 사람에게 맞는 리듬 큐를 바로 주는 AI 에이전트

## 2. 사용자
- **1차:** 집에서 혼자 걷는 파킨슨병 환자
- **2차:** 보호자(가족). 동결이 길거나 잦을 때 알림을 받음

## 3. 문제
파킨슨 환자는 걷다가 발이 바닥에 붙은 듯 갑자기 멈추는 **보행동결**을 겪고, 이때 넘어질 위험이 크다.
메트로놈 같은 리듬 큐가 다시 걷는 데 도움이 되지만, **동결 직후 1초 안에, 그 사람의 걸음 속도에 맞춰** 줘야 의미가 있다.
반대로 일부러 멈춰 섰을 때 큐가 울리면 방해만 되고, 결국 장치를 안 쓰게 된다.

## 4. 왜 엣지·IoT인가
| 이유 | 설명 |
|---|---|
| 지연 | 1초 안에 반응해야 함. 클라우드 왕복 지연과 끊김에 기대면 놓칠 수 있음 |
| 연결 | 집이나 산책 중에는 네트워크가 불안정할 수 있음. 엣지는 오프라인에서도 동작 |
| 프라이버시·대역폭 | 64Hz 원시 가속도는 기기 밖으로 보내지 않고, 이벤트(동결 발생, 행동)만 전송 |

## 5. 데이터
| 항목 | 내용 |
|---|---|
| 데이터셋 | Daphnet Freezing of Gait (UCI, 수업 슬라이드의 whar-datasets 목록) |
| 센서 | 가속도계 3개(발목, 허벅지, 몸통) × 3축, 64Hz |
| 레이블 | 0 = 실험 외, 1 = 정상(걷기·서기·돌기), 2 = 동결 |
| 규모 | 환자 10명, 정상 약 4.5시간, 동결 약 29분, **동결 에피소드 237개** |
| 특징 | 동결 비율이 환자마다 5~26%로 다름(불균형). 10초 넘는 동결 58개 |
| 오탐 테스트용 | **S04, S10**: 동결이 한 번도 없는 환자 |
| 개인정보 | 공개 데이터셋만 사용. 실제 개인·건강 데이터는 생성형 AI에 넣지 않음 |

자세한 탐색 결과: [data_summary.md](data_summary.md)

## 6. 에이전트가 하는 일
감지 모델이 내준 동결 확률을 그대로 따르지 않고, **상황을 보고 행동을 고른다.**
- 걷던 중 멈춘 것인지, 원래 서 있던 것인지 구분해서 **행동하지 않을 때를 안다.**
- 평소 걸음 속도를 스스로 측정해 **그 사람에게 맞는 큐 템포**를 정한다.
- 큐가 안 통하면 강화하고, 길거나 잦은 동결은 보호자에게 알린다.

## 7. 성공 기준
| 기준 | 목표 | 측정 방법 |
|---|---|---|
| 반응 시간 | 동결 감지부터 큐 시작까지 **< 1초** | 결정 로그의 타임스탬프 |
| 감지율 | 동결 에피소드 **80% 이상** 감지 | 237개 에피소드, 환자 단위 교차검증(LOSO) |
| 오탐 | 동결 없는 환자(S04, S10)에게 잘못된 큐 **10분당 1회 이하** | 전체 재생 후 `cue_start` 횟수 |
| 엣지 적합성 | 모델 **< 500KB**, 윈도우당 추론 **< 10ms** | 노트북에서 측정 |
| 엣지 vs 클라우드 | 지연 200~800ms를 넣은 경로보다 반응이 빠름을 수치로 제시 | 반응 시간 비교 그래프 |

> 목표값은 12~13주차 결과를 보고 조정할 수 있음. 조정하면 이유를 보고서에 적는다.

## 8. 한계
- 실제 의료 기기가 아니라 **공개 데이터셋 기반 시연**이다.
- 녹화된 데이터라서 **큐가 실제로 회복을 앞당기는지는 검증할 수 없다.** 시스템이 "언제, 어떤 템포로 큐를 주는가"까지만 평가한다.
- 엣지 기기 없이 노트북에서 시뮬레이션한다. 지표는 노트북 기준이다.
